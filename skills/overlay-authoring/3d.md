# Three.js + glTF authoring

## 経路の振り分け（まずここを判定）

**既定は経路 A（Three.js オーバーレイ）**。経路 B（Blender ベイク、`docs/contract-2026-07-14-3d-bake-recipe.md`）は
A で出せない絵が要るときだけ選ぶ。「タイムラインにクリップとして置きたいから B」は**誤り** —
置き場所ではなく**必要な能力**で選ぶ。

A を既定にする理由（2026-08-04 の実制作で確認）:

- **透過で合成される**。B の出力は不透明な背景を必ず連れてくるので、背景色を合わせ続ける仕事が発生する
  （実際に「なぜ背景が灰色なのか」という手戻りを生んだ）
- **反復が速い**。断片を直して再レンダーで済む（数分）。B は焼き直しに 10 分級かかる
- **画面に映像を流せる**。`materialOverrides` に mp4 を差せば端末画面が動く
- **自作モーションも動く**。Blender で作ったアニメクリップを glb に焼いておけば `animationClip` で再生できる
  （開閉・一周スピン等はこれで足りる。B に逃げる理由にならない）

B を選ぶのは次のいずれかに当てはまるときだけ:

1. **宣言型ランタイムで表現できない絵**が要る — 被写界深度、モーションブラー、レイトレース反射、
   GI、パーティクル、複雑なシェーダ
2. **同時に出す 3D シーンが 3 枚以上**になり、書き出しの性能予算（後述「書き出しが timeout で落ちるとき」）を
   超える。一部を焼いてクリップ化し、同時枚数を 2 枚以下へ落とす
3. 素材ライブラリへ**再利用可能なクリップとして納品**する（レシピ = SSOT の資産にする）

判断に迷ったら A で試す。行き詰まってから B へ落とす方が、B で作り直すより速い。

## 現在の実装ゲート

live preview v0 は、fragment 内の非実行 JSON 宣言を信頼済みランタイムが読み、
ローカル `.glb` の静的シーンと内蔵 animation clip を描画できる。fragment の任意
JavaScript は実行しない。モデルは edit.json 相対パスから preview 専用 localhost
asset URL へ変換され、Three.js core と GLTFLoader は pinned IIFE として同梱される。

export（render-cut）は同じ Three.js runtime を puppeteer-core 経路で動かし、ローカル
`.glb` を自己完結 data URI として埋め込んで 3D overlay を焼き込む。動画 texture・環境マップ画像も
同じく data URI として埋め込む。3D overlay がある edit は HyperFrames 経路を採らず、必ず
puppeteer-core 経路で焼く（`__akariSeek` を呼ぶのはこの経路だけのため）。

export は **動画をフレーム精度でシークし、提示フレームが確定してから 3D を描く**。この順序が
逆だと `<video>` が 1 フレーム前の絵のまま texture へ上がる（実測: 旧順序は全フレームが
ちょうど 1 コマ遅れる）。

根拠: `packages/overlay-runtime/src/overlay-runtime.js`、
`packages/overlay-runtime/src/three-runtime.js`、[WHATWG HTML — scripting](https://html.spec.whatwg.org/dev/scripting.html)

## 宣言型 fragment スキーマ（preview v0）

fragment は単一ルートとし、透明 canvas、任意の静的 fallback、非実行の
`<script type="application/json" data-akari-3d-scene>` を 1 個だけ置く。

```html
<div class="product-spin">
  <canvas class="product-spin__canvas"></canvas>
  <div data-akari-3d-fallback>3D を読み込み中</div>
  <script type="application/json" data-akari-3d-scene>
  {
    "model": "assets/models/product.glb",
    "camera": {
      "position": [0, 1.2, 3],
      "fov": 45,
      "near": 0.1,
      "far": 100,
      "lookAt": [0, 0.5, 0]
    },
    "environment": {
      "intensity": 1.0,
      "exposure": 1.0,
      "map": "assets/env/studio.png"
    },
    "shadows": true,
    "lights": [
      { "type": "ambient", "color": "#ffffff", "intensity": 0.35 },
      {
        "type": "directional",
        "color": "#ffffff",
        "position": [2, 3, 2],
        "lookAt": [0, 0.5, 0],
        "intensity": 1.2
      }
    ],
    "materialOverrides": {
      "ScreenMaterial": { "texture": "assets/screens/app-01.png" }
    },
    "animationClip": "Idle"
  }
  </script>
</div>
```

- top-level key は `model` / `camera` / `environment` / `lights` / `animationClip` / `materialOverrides` / `shadows` だけ。
- `model` は edit.json のあるディレクトリからの相対 `.glb` パス。URL や CDN を書かない。
- camera は perspective camera。`position` / `lookAt` は `[x, y, z]`、`fov` / `near` / `far` は数値。
- `environment` は IBL の knob。`intensity` は金属など PBR マテリアルへの環境光強度、
  `exposure` は ACES Filmic tone mapping の露出で、どちらも 0 以上の数値を指定する。省略時は
  `intensity` は `0.5`、`exposure` は `1.0`。まず既定値で
  確認し、白飛びを抑えるなら `exposure`、映り込み自体の強弱を変えるなら `intensity` を小幅に調整する。
  IBL 自体（既定値での環境マップ・トーンマッピング）は preview / export とも常に有効 — `environment`
  キーは既定値からの微調整用の任意 knob。
- `environment.map` は**正距円筒（equirectangular）画像の相対パス**。宣言すると既定の手続き生成
  `RoomEnvironment` を差し替える。金属は環境の映り込みでしか見えないので、光源に「形」が要る
  ヒーローカットではこれが効く（既定の部屋は強度スカラーしか触れず、側面レールが黒く沈む）。
  画像形式のみで動画は受け付けない。読み込みは load 完了まで待ってから ready になるので、
  「既定の部屋のまま焼ける」ことはない。**環境光の強度を上げて材質の不足を埋め合わせないこと** —
  副作用（画面の白濁・彩度飛び・白飛び）が離れた場所に出る。
- `shadows` は真偽値、または `{ "enabled": true, "mapSize": 2048, "bias": …, "normalBias": … }`。
  **既定は無効**（既存素材の見え方を変えないため、素材側で明示的に宣言する）。有効にすると
  shadow map を立て、メッシュへ cast / receive を、`directional` ライトへ影の投射を配線する。
  shadow camera はモデルの実寸（bounding sphere）へ自動で畳むので、数 cm の被写体でも影が出る。
  `bias` / `normalBias` の既定も実寸から決まるため、通常は宣言しなくてよい。
  **自発光マテリアルのメッシュは cast / receive の対象から外れる**（光源側の扱い。発光体が
  自分の影で汚れるのを避ける）。
- light type は `ambient` または `directional`。directional は `position` と `lookAt` を宣言できる。
- `animationClip` は glTF 内蔵 clip の正確な名前。**clip 名の配列**、または全 clip を同時再生する
  `"*"` も指定できる。省略時は静的シーンを描画する。Blender の glTF 書き出しはオブジェクトごとに
  clip を分けるので、1 個のモデルに複数の動きがあるときは `"*"` で束ねる（1 本しか再生しないと
  片方しか動かない）。存在しない clip 名を書いた場合はエラーになる。
- `materialOverrides` は `{ "<material 名>": { "texture": "<画像または動画の相対パス>" } }` の形で、名前が一致するマテリアルの `emissiveMap` を差し替える。edit.json のあるディレクトリからの相対 PNG / JPEG / WebP 等、または MP4 / MOV / WebM を指定し、URL や CDN を書かない。該当するマテリアル名がモデル内にない場合は警告して無視される。
  - **パスは「edit.json のあるディレクトリ」から。断片の場所からの相対ではない。** `model` も同様。
    断片を `overlays/3d-phone/fragment.html` へ置いたなら `"overlays/3d-phone/model.glb"` と書く
    （`"model.glb"` はプロジェクト直下を探して ENOENT になる）。
  - **貼っても真っ黒 / 何も変わらないときの 2 大原因**（2026-08-04 実測）:
    (1) 対象メッシュに **UV が無い**。glTF の `TEXCOORD_0` が無いメッシュにはテクスチャが乗らない。
    Blender で uv_layers を新規作成して平面投影してから再エクスポートする。
    (2) 差し替え先は `emissiveMap` なので、**マテリアルの emissive が黒（既定）だと結果も黒**。
    glb 側で emissiveFactor を白・Emission Strength を 1.0 にしておく。
- canvas は CSS で表示寸法を必ず与える。fallback に `data-akari-3d-fallback` を付けると load 完了時だけ隠れる。fallback は自由にスタイルしてよく、`display` を宣言しても load 完了時にランタイムが確実に隠す。

## 標準ツマミ（camera 投影 — pan / zoom。2026-08-06 導入）

ランタイムは `--akari-3d-pan-x` / `--akari-3d-pan-y` / `--akari-3d-zoom` という 3 つの
**標準カスタムプロパティ**を解釈する。断片ルート（または祖先）へ CSS で宣言すると、
ランタイムが毎 draw 読み取り、**カメラの投影**（`setViewOffset` によるオフセット、
`fov` の詰め直し）へ反映する。カメラ位置・モデル姿勢・ライトには一切触れない
（焼き込み済みアニメーションクリップとの干渉を避けるため）。

| プロパティ | 意味 | 単位 |
|---|---|---|
| `--akari-3d-pan-x` | 被写体の横位置。フレーム幅に対する割合 | `%` 付き、または無単位の小数（`50%` = `0.5`） |
| `--akari-3d-pan-y` | 被写体の縦位置。フレーム高さに対する割合。正 = 下へ（既存 CSS `translate` と同じ向き） | 同上 |
| `--akari-3d-zoom` | 見かけの大きさ倍率。`1` = 既定 | 無単位 |

**単位は割合に統一する（px にしない）。** プレビューは表示倍率で縮小されることがあり、
px 単位だと表示倍率に依存してプレビュー / 書き出しの絵が食い違う（パリティが壊れる）。
割合なら表示倍率と無関係に一致する。

### 経路A の canvas 移動 CSS を置き換える

旧来、素材のツマミ（`--<asset>-x` / `--<asset>-y` / `--<asset>-scale` 等）は断片ルートの
`transform: translate(...) scale(...)` を通じて **canvas そのものを CSS で動かして**いた。
これは canvas がフレーム外へ出て見切れる・拡大が描画済みビットマップの引き伸ばしになる
（解像度が落ちる）という欠陥がある。標準ツマミへブリッジすることでどちらも解消する:

```css
.laptop-live {
  position: absolute; inset: 0;
  --akari-3d-pan-x: var(--laptop-live-x, 0);
  --akari-3d-pan-y: var(--laptop-live-y, 0);
  --akari-3d-zoom:  var(--laptop-live-scale, 1);
}
```

素材ごとのツマミ名（`--laptop-live-x` 等）はそのまま維持し、標準プロパティへ**マップするだけ**。
`transform` は撤去する。canvas は常に `inset:0` でフレーム全面を覆い続け、被写体が消えるのは
本当にフレーム外へ出たときだけになる（自動見切れ補正は無い — 意図したはみ出し演出をそのまま描く）。

### 後方互換

**3 プロパティが未宣言なら現行と完全に同一挙動。** ランタイムは `getComputedStyle` で 3 つとも
空文字（＝どの祖先も宣言していない）と分かった時点で `camera.view` に一切触れない
（`setViewOffset` を呼ばない・`fov` も書き換えない）。旧来の CSS `transform` 方式の断片は
無改修のまま動き続ける。

### パリティ（プレビューと書き出しが同じ絵になる理由）

書き出し（`packages/render-cut/src/rasterize.mjs` の `embedThreeModels`）とライブプレビュー
（shell / `packages/overlay-runtime/src/overlay-runtime.js`）は**同じ `three-runtime.js` を
同じ断片 DOM 構造へ注入する**。標準プロパティは断片ルートで宣言され、CSS の継承で
`<canvas>` まで届く — 呼び出し元がどんな入れ子（`.scene-content` で包む／包まない等）で
container を渡しても、断片の外側からは同じ値が同じ式で読まれる。store の簡易レンダラー
（`asset-live.js` の `mountThreeScene`）は `three-runtime.js` を使わない独立実装のため、
**同じ式・同じ符号を手動で移植する**必要がある（移植を怠ると、それだけがプレビューと
書き出しからズレる）。

## 書き出しが `seeking frame N timeout` で落ちるとき

書き出しのラスタライズはヘッドレス Chrome の **ソフトウェア WebGL**（GPU 無し）で走る。
1920×1080 のシーンを毎フレーム CPU で描くので、**同時に出す 3D シーンが増えるほど 1 フレームが重くなり**、
60 秒のウォッチドッグに触れて書き出し全体が失敗する。実測（2026-08-04・M 系 Mac）:

| 同時 3D シーン | 1 フレームのシーク | 結果 |
|---|---|---|
| 1 枚 | 数十 ms | 安定（8/8 成功） |
| 2 枚 | 数百 ms | ほぼ安定（稀に失敗） |
| 3 枚 | 300 → 1500ms と漸増 | 連続失敗（ページごと固着する瞬間もある） |

- **同時に出すシーンは 2 枚までを目安に**。3 枚以上ならショットを時間でずらす（同時刻に重ねない）
- 失敗時は警告に直近フレームの所要時間・3D シーン数・ページの声が出る。
  **時間が伸びていれば「重すぎる」、伸びずに固まっていれば別要因**という読み方をする
- タイムアウトは相関で犯人を決めない。**1 変数だけ変えて複数回**回して初めて因果が言える
  （2026-08-04 の実例: 「自作アニメ glb が原因」→ 棄却、「environment ツマミが原因」→ 棄却、
  実態は上表の性能限界。誤診 2 回のコストを診断出力で減らすのがこの節の目的）

## 原則

- 3D は Three.js、交換形式は glTF 系に限定する。preview v0 は外部 buffer を持たない自己完結 `.glb` と、`materialOverrides` で指定したローカル画像を受け付ける。Draco/KTX2 は未対応。
- Three.js 本体、addon、decoder、model、texture はローカルへ固定し、CDN import を使わない。export Chrome は background network を無効化する。
- fragment は上記の宣言型スキーマに限定する。任意 script、event handler、`new Function()` 等を使わない。
- 単一ルート内へ透明 canvas と静的 fallback を置く。canvas は透明合成を有効にし、背景を不透明に塗りつぶさない。
- asset は visible な期間だけ load / render / decode され、区間外と unmount で geometry、material、texture、renderer が解放される。
- camera、light、model pose、material、screen source を CSS 変数または素材 metadata の knob として宣言する。固定すべき model topology まで knob にしない。

## ライセンス済み glb

1. 配布元、asset ID / version、author、取得日、license、商用可否、改変可否、帰属表示を確認する。
2. glTF 形式であることを利用許諾と取り違えない。license 不明の model は使わない。
3. library からリンクせず、採用する project へ `.glb` と必要 texture / decoder をコピーする。
4. project 側 provenance に元 library、version、license、attribution を残す。
5. 相対 URL で読み込み、load error 時に空 canvas のまま成功扱いしない。

素材ライブラリ利用時のコピー規律は `docs/contract-2026-07-13-asset-library.md` に従う。

## 決定的な 3D アニメーション

- preview v0 は overlay の local timeline 秒を `AnimationMixer.setTime(localSeconds)` に渡し、その状態だけを render する。
- `THREE.Clock` や `mixer.update(delta)` で時間を積算しない。カメラ、shader time、particle も同じ local timeline から求める。
- rAF は算出済みの時刻を描画するためだけに使い、rAF delta を状態へ足さない。
- glTF clip がない動きも、local time の関数として pose を求める。再生・停止・逆シークで同じ結果になることを確認する。

公式: [Three.js AnimationMixer.setTime](https://threejs.org/docs/pages/AnimationMixer.html#setTime)

### クリップ長は overlay の窓尺に一致させる（実測 2026-08-04）

`setTime(localSeconds)` の駆動で、**clipAction は既定 LoopRepeat**。窓（`duration`）がクリップ長を
超えると、超えた瞬間にクリップ先頭へ巻き戻り、**モデルが破綻したように見える**（開いた蓋が
一瞬で閉じる等）。

- 対処は 2 択: (a) 窓をクリップ長以内に収める (b) **クリップを窓尺ぴったりに作り直す**
- 同梱クリップの尺・向きが用途に合わないことは珍しくない。合わないなら**作り直す方が速い**
  （§glb を直接編集する）

### モデルの「既定ポーズ = 中立」と決めつけない（実測 2026-08-04）

ノート PC の `lid_root` で、回転 0°（単位クォータニオン）が **「閉じ」ではなく「180° フラット
（開ききって平ら）」** だった実例がある。実際の開き角は `180° − A`（A = 適用した X 回転角）。

| 適用角 A | 実際の見え方 |
|---|---|
| 0° | 180° フラット |
| 100° | 通常の開き 80° |
| 180° | 完全に閉じ |
| −100° | 逆折れ 280°（ヒンジが反対側へ） |

**角度の意味は必ず実レンダーで 3 点以上（両端 + 中間）を撮って確定させる。**
モデル名・軸名・既定値からの推測で決めない。

### glb を直接編集する（Blender より確実な場面がある）

- **Blender の `frame_set()` はポーズ凍結に使えない**: glTF 読み込み直後はアニメが評価されず、
  どの時刻を指定しても既定ポーズのまま出力される（複数時刻で同じ絵が出たら疑う）
- ノード回転の差し替え・アニメの新規生成は **glb の JSON チャンクを直接書く方が確実**
- 実装メモ:
  - BIN チャンク末尾へ **4 バイト境界を守って append** し、`bufferViews` / `accessors` を追加 →
    sampler から参照する
  - `buffers[0].byteLength` と **GLB ヘッダの総長**を更新し忘れない
  - 時刻（input）accessor には **`min` / `max` が必須**
  - 回転の `LINEAR` 補間は SLERP なので、30fps 相当のキーを並べれば任意のイージングを再現できる
  - 静止 `node.rotation` も t=0 の値に揃える（初回描画のちらつき防止）

### テクスチャが載らないモデルへ焼き込む

`materialOverrides` は既存の `emissiveMap` にしか効かず、**UV も emissive も持たないマテリアルには
構造的に効かない**（画面が黒いまま）。その場合は Blender で平面 UV を張り、画像を
`emissiveTexture` として焼き込む（`emissiveStrength` 1.2〜1.5 目安）。

**UV の向きは 4 通りを実レンダーで総当たりするのが速い**（bbox 軸から機械的に決めても向きは出ない）:
`(u,v)` / `(1-u,v)` / `(u,1-v)` / `(1-u,1-v)`。判定基準は「文字が正しく読めるか」。

## VideoTexture

`materialOverrides` の texture に動画（`.mp4` / `.m4v` / `.mov` / `.webm`）を指定すると、ランタイムが
`<video>` を DOM へ置いて `VideoTexture` を作る。**DOM へ置くのが要点** — 決定的シークは
`document.querySelectorAll('video')` を対象にするので、DOM にいるだけで既存の機構に乗る。

- 時刻を決めるのは常に**外側**。ランタイムは `autoplay` しない。wall-clock 再生へ任せない。
  - **export**: rasterize がフレーム精度シーク（提示フレームの確定まで待つ）を済ませてから
    3D を描く。ランタイムは `currentTime` を書かない
  - **preview**: tick が `render(container, seconds, { syncVideos: true })` を渡し、ランタイムが
    overlay のローカル時刻へ `currentTime` を合わせる。壁時計で進むので提示フレームの確定は
    待たず、1 フレーム前後ずれることがある（絵は必ずその時刻の近傍になる）
  - `syncVideos` は **preview 専用の opt-in**。export で渡すと確定済みの提示フレームを崩して
    決定性が壊れる
- ランタイムは `<video loop>` を立てて作る。export のシークは loop 宣言のある素材の時刻を尺で
  畳むので、素材より合成が長くても末尾で静止せず巻き戻って回る。
- **編集用 720p プロキシ**を与える。原本を texture へ接続しない。export は動画を data URI として
  シートへ埋め込む（base64 で約 1.37 倍）ので、原本を差すとシートが肥大し、preview は
  それを毎 tick シークすることになる。
  - **24MiB を超える動画 texture は export が拒否する**（黙って原本へ fallback しない）。
    エラーには 720p プロキシを作る ffmpeg コマンドが出る:
    `ffmpeg -i <master> -vf scale=-2:720 -c:v libx264 -crf 23 -preset medium -pix_fmt yuv420p -an <proxy>.mp4`
  - 解像度ではなくバイト数で見ているのは、シート生成が同期・純関数で ffprobe を呼ばないため。
    「720p かどうか」の代理指標であり、上限そのものは運用で調整してよい
  - タイムライン素材側の `source.proxy`（edit.json）の自動生成は別件で、現時点では未実装
- ミップマップはランタイムが有効化する（`LinearMipmapLinearFilter` + 異方性 16）。
  `VideoTexture` の既定は無効で、大きな画面素材を 3D 上の小さな面へ潰すと細部が割れ、
  モデルが回ると割れ方が毎フレーム変わるため「カクついている」ように見える。
- 差し込み先の面は **baseColor を黒**にする。明るいままだと環境光で照らされた面が
  自発光の絵を飲み込む。UV の無いメッシュには差せない（(0,0) を拾って真っ黒になる）。
- 素材の縦横比を差し込み先に合わせる。縦動画を横画面に差すと引き伸ばされる。
- source の寸法・format を変える場合は既存 texture を dispose し、作り直す。
- preview は毎 tick シークするため、**編集用 720p プロキシでないと詰まる**。原本を差さない。
  既に十分近い時刻（20ms 以内）なら書かないので、再生中にシークが走り続けることはない。

公式: [Three.js VideoTexture](https://threejs.org/docs/pages/VideoTexture.html)

## パフォーマンス

- 4K 上の post-process blur、`filter: blur()`、`backdrop-filter`、過剰な shadow を使わない。
- `shadows` を有効にすると shadow map の深度パスが増える（実測: 単純なシーンで draw call 2 → 4）。
  必要なカットだけで宣言する。
- 動画 texture は毎フレーム GPU へ上げ直す。ミップマップの再生成もそのたびに走る。
- 毎フレームの object / material / texture 生成、shader compile、model reload を避ける。
- preview v0 と export の renderer pixel ratio は `1` 固定。同一 scene の見え方を対象出力 profile で実測する。
- `renderer.info` で draw calls、triangles、textures を計測する。固定の polygon / draw-call 上限は一次根拠がないため発明せず、対象 Mac と出力 profile で **要検証** とする。

公式:

- [Three.js GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)
- [Three.js — How to dispose of objects](https://threejs.org/manual/en/how-to-dispose-of-objects.html)

## よくある間違い

- CDN の Three.js、decoder、texture に依存する。
- Draco / KTX2 圧縮モデルを v0 へ渡す（decoder と worker は未対応）。
- license 不明の `.glb` を「ネットで見つけた素材」として同梱する。
- JSON 宣言の代わりに fragment 内の `<script>` を実行させようとする。
- export だけを見て WYSIWYG 対応済みと報告する。
- proxy がないため原本を `VideoTexture` へ流す。
- 材質にテクスチャが無いまま `environment.intensity` を上げて金属をごまかす（副作用が離れた場所に出る）。
- 複数の動きを持つモデルで `animationClip` を 1 本だけ指定し、片方しか動かないまま出す。
- overlay の窓尺がクリップ長を超え、途中でループして破綻する。
- モデルの既定ポーズを「中立（閉じ・正面）」と決めつけ、実レンダーで角度の意味を確かめない。
- Blender の `frame_set()` でポーズを凍結したつもりになる（アニメが評価されず既定ポーズのまま）。
- `Clock.getDelta()` / `mixer.update(delta)` でアニメーションする。
- 非表示後も render loop と video decode を動かす。
- dispose せず、素材切替のたびに GPU resource を残す。
