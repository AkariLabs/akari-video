- 経緯: 「SDK とハーネスはどう違うのか / SDK 的な売り方がいいのか」という問いから出発し、
  (a) レイヤー整理と売り方判断の保留、(b) UI の再定義（編集ツールではなくレビューツール）、
  (c) アノテーション対象の型分類、(d) 素材が無い状態から始めるための仮枠タイムライン

## 0. SDK とハーネスの整理 — 競合する売り方ではなく同じものの別レイヤー

区別は**「誰が呼び出すか」**の一点:

- **SDK**: 人間の開発者が自分のコードに組み込む部品集。呼び出すのは他人の書いたプログラム
- **ハーネス**: AI エージェントが仕事を遂行するための足場（スキル・CLI・ビューアー・分析）。
  呼び出すのは Claude / Codex

現在作っているスキル・ビューアー・分析は全てハーネス側。ただしハーネスの中心には
**決定論的な編集エンジン**（カット・字幕合成・レンダリング等 = ただのコード）が埋まっており、
これを切り出したものがそのまま SDK になる:

```
[人間向け UI (プレビュー+注釈)]     [AI エージェント (Claude/Codex)]
        │                                │ ← ここがスキル（ハーネス）
        ▼                                ▼
   [編集エンジン = 将来 SDK として切り出せるコア]
        │
   [セーブデータ (edit.json + サイドカー群)]
```

### 判断

- **売り方（SDK=toD / アプリ=toC）は今決めない**。コアとガワの分離を保っていれば
  どちらも後から選べる。市場が違うだけで排他ではない
- 「究極体（全部自然言語）」と「人間が微調整するアプリ」も分岐ではなく、
  **同一アーキテクチャ上の 2 つの UI モード**。どちらも同じエンジンと同じセーブデータを触る
- 規律: **決定論的にできる処理をスキル（プロンプト）側に書きすぎない**。コードに寄せ、
  スキルは「いつ何を呼ぶか」の判断だけにする。この境界がそのまま将来の SDK 境界になる

既存文書との関係: サンドイッチ 3 層（design-2026-07-13 §4）・headless-first
（notes-2026-07-16 §1）と同じ結論の別断面。本項は「販売形態の観点から見ても
同じ分離が正しい」ことの確認。

## 1. UI の再定義 — 編集ツールではなくレビューツール

編集の実行主体は AI（design-2026-07-13 §1「アプリは確認して直す場所」）。これを突き詰めると、
UI の仕事は「編集操作を提供すること」ではなく
**「人間のフィードバックを高解像度で捕まえること」**に変わる。

### 究極体 UX

- デフォルト表示は**動画プレビュー + タイムラインのみ**。フォルダツリー・プロパティ等は
  「AI に正確に指示するために人間が見たい時」だけ任意表示
- 再生しながら喋る / ペン・矩形で囲う →
  タイムスタンプ + 座標 + 発話書き起こしのアノテーションとして記録 → AI が解釈して編集 →
  再生して QA、の往復が主ループ
- 編集操作の UI を人間に覚えさせない。像としては
  「Frame.io 的レビュー UI + 編集者としての AI」の組み合わせ
- 自然言語より直接操作が的確な場面（絶妙なニュアンスの微調整、notes-2026-07-16 §0）の
  受け口は残す。タイムライン微調整はその代表

## 2. アノテーション対象の型分類

アノテーションは `{対象 target, 意図 intent, 本文 body, 参照 refs}` の 4 つ組。
本文は発話書き起こしまたはテキスト。target の型は 5 種:

| target 型 | 例 |
|---|---|
| 時刻（瞬間） | 「今のこのタイミング」 |
| 時間範囲 | 「ここからここまでをこうしたい」 |
| 空間範囲 × 時間範囲 | 「この範囲のこのオブジェクト」（矩形・フリーハンド） |
| 素材参照 | 「この素材をどうしたい」 |
| 挿入点 | 「ここに B-roll を入れたい」（位置 + 挿入意図 + 任意の素材参照） |

- **ペンか矩形かは入力手段の差でしかなく、データは同じ「空間範囲」に落ちる**。
  型を固めておけば UI 側は入力手段（音声・ペン・矩形・テキスト）を後から自由に足せる
- 収載先はセーブデータのサイドカーを想定（応答 3 チャネルとの関係整理は契約昇格時）
- 命名注意: 既存の `.akariamt.json`（akari-amt = 口パク・アバタートラック）とは別物。
  契約化時に衝突しない名前を選ぶ

## 3. 仮枠タイムライン — 正体はアニマティクス

素材がまだ無いパターン（AI 生成 / これから撮影する）では、分析から入る現行フロー
（analyze-footage → 編集判断レポート）が使えない。代わりに:

1. **対話で方針を決める**: 質問ベース・選択肢式（ABC 回答形式）で深掘り
2. **プラン確定** → **仮枠タイムライン**を生成

仮枠の正体は映像業界の**アニマティクス（V コンテ）**: 静止画 + TTS 仮ナレーション +
テキストカードで尺とテンポを先に確定させ、高コストな工程（動画生成・撮影）の前に
方向性の QA を済ませる。

### パイプライン（コスト昇順）

```
対話（質問形式で方針決め）
  → プラン確定
  → 仮枠タイムライン（静止画 + TTS + テキストカード）   ← 安い
  → 再生して QA「この方向でいい?」
  → 本生成 / 撮影                                      ← 高い
```

- 「一気に生成してから直す」か「段階的にやる」かは二者択一ではない。
  **確度に応じてステップを飛ばせる 1 本のパイプライン**とする:
  方向性が固い場合（既存素材の分析から入る等）は仮枠をスキップして一気に組んでよく、
  方向性が不確かな AI 生成パターンでだけ仮枠が効く
- 動画生成の前に**画像生成（1 枚目の絵）+ 読み上げだけでタイムラインを組んで QA する**のが
  最も無駄がない、が本項の中核判断

## 4. 「HTML レポートかタイムラインか」の解 — 同一プランデータの 2 レンダリング

方針レポート（編集判断レポート、contract-2026-07-13-m5）と仮枠タイムラインは対立しない。
**プランをデータとして持ち、文章として読むならレポート表示、時間軸で見るなら
タイムライン表示**という同一データの 2 レンダリングとする。
HTML レポートの根拠（notes-2026-07-16 §1）はそのまま保持される。

「正解のないタイムラインになる」問題は、スロットに**確定度**を持たせて解く:

| 状態 | 意味 | 表示 |
|---|---|---|
| `locked` | 制約として確定（「尺 30 秒のケツ」「ここに効果音」等の決定事項） | 固定表示 |
| `proposed` | 仮説（「たぶんここにこう入る」） | ゴースト表示（点線・半透明） |
| `filled` | 素材が実際に入った状態 | 通常表示 |

確定事項と仮説が見た目で区別できれば、仮説だらけのタイムラインを表示しても嘘にならない。

## 5. スロットの充填手段 — generate / record / import

仮枠の空きスロットは、その時点で**プラン由来の台本と目標尺を既に知っている**。
充填手段は 3 種で、スロット定義に充填手段フィールドを最初から予約しておく:

- `generate`: AI 生成（§3 の画像先行 QA を経て動画生成）
- `record`: 画面収録 / カメラ収録。空きスロットから即収録開始 →
  **テレプロンプターに台本表示 → 喋るだけ** → 収録物がスロットに入り字幕生成へ。
  画面収録 + テレプロンプター自体は標準技術（getDisplayMedia 等）で実装難度は低い
- `import`: 既存素材の割り当て

収録統合は後回しのマイルストーンでよいが、新しい概念は不要
（スロットを埋める手段が 3 つある、というだけ）で、仮枠の設計にほぼ差し込みで入る。

## 6. 実装への接続

- 最初に固めるのは UI ではなくデータ 2 点:
  1. **アノテーション形式**（§2 の 4 つ組 + target 5 型）
  2. **プラン形式**（確定度つきスロットの列、§4–5）
  UI・スキル・生成・収録はすべてこの 2 つの周辺装置
- いずれも契約昇格時は `contract-` 文書として edit.json サイドカー群に位置づけ、
  版管理原則（contract-2026-07-17）に従う
- 仮枠の生成スキルは編集判断レポート（contract-2026-07-13-m5）の生成スキルと
  プランデータを共有する形で統合を検討
- 質問ベースの方針決め対話は企画ステージスキル（skills/）の手順として規約化する
