## 0. 位置づけ — 一言で言い切る

承認は本質的に**机の前にいなくてもできる**。解析・レンダはマシンが回し、人間は「レポートを見て
OK / 差し戻しを言う」だけ — その閲覧と素材の受け渡しを、道具 1 つ（Tailscale）のセットアップで
スマホから可能にする。私設ネットワーク限定 = **デフォルト非公開**であり、「設定ミスで世界に公開
されていた」が構造的に起きない手段だけを既定とする。

## 1. 決定事項（v0 の骨格）

| 論点 | 決定 |
|---|---|
| 手段 | **Tailscale**（tailnet 限定）。閲覧 = `tailscale serve` でプレビューサーバーと承認レポートヘルパーを tailnet 限定 HTTPS 化。素材 = **Taildrop**（共有シートからデバイス直送。クラウド不経由・実用上サイズ無制限・画質劣化なし） |
| 不採用 / 保留 | Cloudflare Tunnel + Access（tailnet 外の人への共有が要件になったときの**別契約**。「公開してからゲートで守る」構造は既定にしない）。Cloudflare Pages（レポートはローカル随時生成のため噛み合わない） |
| 素材搬送路の優先順位 | **Taildrop（v0 で実装）** → Dropbox カメラアップロード → iCloud 写真 → Google Drive（順次。v0 では選択肢として提示のみ）。Google フォトは対象外（Library API 制限により自動取得不可） |
| 対応 OS | macOS / Windows 両対応を前提に書く（Tailscale / Taildrop とも両対応。手順の分岐は SKILL.md 側） |

## 2. スキルの責務 — 5 フェーズ

1. **doctor**: Tailscale の導入状態を決定論で判定（未導入 / 導入済み・未ログイン / 構成済み）。
   プレビューサーバーの起動可否・serve 設定の現況もここで検出
2. **導入ガイド — 人間手番の受け渡し**: インストーラーの sudo・GUI ログイン・スマホ側アプリ導入は
   **自動化しない**（macOS の cask は .pkg で sudo 対話必須 — 実測済み）。スキルは
   「ここはあなたの番」を明確に指示 → 完了を doctor で確認 → 次へ進む、を繰り返す構造とする
3. **serve 設定**: `tailscale serve` で許可リスト（§3）の 2 件を tailnet 限定 HTTPS URL にする。
   外部から見える口を安定させるため、**外部ポートを固定し内部ポートを写像する**形を既定とする:

   | 外部 | 内部 | 中身 |
   |---|---|---|
   | `https://<host>.ts.net/` | 4567 | プレビューサーバー |
   | `https://<host>.ts.net:8443/` | ヘルパーの動的ポート | 承認レポート + `decisions.json` |

   レポートヘルパーの内部ポートは起動ごとに変わりうるが、外部 URL は固定される（チャットに
   貼ったリンクが起動のたびに死なない）。パス分岐（`--set-path /report`）はプレフィックス
   除去の挙動を実測してから選択肢に加える — 未実測の間は既定にしない
4. **Taildrop 受信設定**: 受信先フォルダを固定し、作業場の `inbox/` へ接続する
   （直接指定できる場合は直接、できない場合は受信箱 → `inbox/` への移送手順を案内）
5. **疎通確認**: 別デバイスから (a) serve URL が開ける (b) テストファイルを Taildrop 送信して
   `inbox/` に現れる — の両方が通ったら、URL と受信経路を完了レポートに記録して終了

## 3. 安全規律（ハードルール）

- 既定は **tailnet 限定のみ**。公開インターネットへ出す `tailscale funnel` は**既定で使わない・
  提案もしない**。ユーザーが明示的に要求した場合のみ、リスク説明 + 明示承認を経て扱う
- serve してよい対象は**次の許可リスト 2 件に限る**（2026-08-12 拡張）:
  - (a) **プレビューサーバー**（`akari --preview`、既定 4567）
  - (b) **decision-cards レポートヘルパー**（`packages/decision-cards/report-helper.mjs`。
    承認レポートの配信と `decisions.json` の read / write / commit を担う。`127.0.0.1` バインド）

  これ以外のポート・アプリ・ファイルシステムは serve しない。許可リストを増やすときは
  **本契約を改訂してから**行う（スキル側の判断で足さない）
- secrets を作業場・プロジェクトに書かない（creator-root v1 の原則。Tailscale の認証情報は
  Tailscale 側が管理し、スキルは一切保持しない）
- スキルが勝手にインストールを完遂しない（§2-2 の人間手番）。ネットワーク設定の変更は
  すべて事前提示 + 承認後に実行

## 4. intake との接続

- Taildrop の受信先 → 作業場 `inbox/`（creator-root v1 §3 の投げ込み口）が受け皿
- 「直近で撮ったやつで編集よろしく」の**自動選択規約（直近 N 件 / 直近 24h 等）は v0 では
  定めない** — 人間が `inbox/` 内のファイルを指す運用でよい。自動選択は intake 側の将来契約
- クラウド同期レーン（Dropbox 等）を使う場合も「同期フォルダ = 監視対象」に正規化される設計を
  崩さない（搬送手段が何であれ、最終形は「ローカルフォルダにファイルがある」）

## 7. L2 実測記録（2026-08-12・オーナー実機 iPhone + macOS）

**通った項目**:

| 検証 | 結果 |
|---|---|
| 別デバイスからのプレビュー閲覧 | ✓ tailnet 経由で表示。体感速度は「十分すぎる」（WireGuard 直結のため） |
| **レポート内に埋めた動画の再生** | ✓ iOS 実機で再生・**シーク成功**（H.264 640x360 / 6 秒） |
| Taildrop 着弾 | ✓ 受信先の実パス = **`~/Downloads/`**（macOS GUI 版・実測で確定） |
| Taildrop の無劣化性 | ✓ 92MB / HEVC / 1180x2556 / 60fps / **15.7Mbps のまま**再エンコードなし |
| Taildrop → 作業場 `inbox/` | ✓ **移送運用**で接続（`~/Akari/inbox/`）。macOS スタンドアロン版は受信先を設定変更できないため、直接指定ではなく移送を採る（§2-4 の想定どおり） |

- Taildrop の実測は「チャット添付は搬送路として筋が悪い」（§非スコープの根拠）を裏づけた —
  同じ 92MB は Telegram Bot API 標準（受信 20MB）では原理的に通らない
- 受信物が HEVC だった点は、プレビューサーバー側の H.264 自動プロキシ層が実運用で必要になることの実例

**未達の項目（L2 は未クローズ）**:

| 未達 | 状況 |
|---|---|
| HTTPS | **`tailscale serve` の TLS が未成立**。tailnet 側で HTTPS は有効（`CertDomains` に当該ドメインあり）だが Let's Encrypt の ACME 注文が `invalid` で失敗。上記の実測は tailnet 内の平文 HTTP で代替した（WireGuard 内側のため機密性は保たれるが、secure context を要する機能は使えない）。**平文 HTTP を既定にはしない** |
| `decisions.json` の往復 | 未実測。検証に使ったレポートに決定カードを載せなかったため。カード操作 → 保存の往復は別途要実測 |
