- 日付: 2026-07-16
- 状態: 方向性メモ（オーナーとの設計会話の記録。契約への昇格は各項の実装着手時）
- 経緯: 外部の設計対話（Theia フォーク / トランスクリプト駆動編集の一般論）を既存契約と
  突き合わせてレビューした。大半は既存決定（analysis.json + edit.json の二層、MCP 縮小、
  キーフレーム 3 系統等）と同一結論であり採録不要。本メモは**差分として採択した項目**と、
  **明示的に不採用とした項目**のみを記録する

## 0. 不採用の記録（再検討しない）

| 提案 | 不採用理由 |
|---|---|
| Theia AI（チャット UI + ツール呼び出しフレームワーク） | ハーネス非依存の invariant（PTY + ファイル契約、Claude Code / Codex 両対応）と衝突。Theia のエージェント層にロックインされる。Theia は「箱」としてのみ使う |
| コマンドパターン（UI とエージェントが同一ツール関数を叩く） | 本設計の合流点は関数ではなく**セーブデータ**（人間の操作は edit.json / data 属性 / CSS 変数に着地、エージェントはスキル + スクリプトで read-modify-write）。相互運用性は同等で、ツール API 層という結合を増やさない |

ツールの使い分け自体は既存決定の通り: コア編集 = セーブデータ直接書き込み、
MCP は読み取り/実行系と外部連携（生成・ストック素材検索）のみ
（design-2026-07-13 §1、contract-2026-07-13-m5 生成スキル契約）。

## 1. edit-lint — 決定的バリデータ（QA ステージスキル）

フィードバックループを**二階建て**として明示する:

| 層 | 実体 | 状態 |
|---|---|---|
| 意味的検証 | エージェントが検証フレームを視認して品質確認 | Step 1 実験で確立済み |
| 決定的検証 | **edit-lint**（本項。未整備） | 新規 |

「ツールは実行エラーを出さないが、意味エラー（60 秒指定なのに 63 秒）は出る」ため、
編集の実行が成功しても結果が制約を満たすとは限らない。決定的にチェックできるものは
普通のコードで検査する。

### チェック項目（v0 候補）

- `cuts` の昇順・非重複・source 尺内
- 合計尺 vs `outputs[].duration_max`（ショートの 60 秒制約等）
- `overlays` の start/duration がタイムライン尺からはみ出していないか
- 参照ファイルの実在（オーバーレイ HTML 断片・audio.bgm/sfx のパス・サムネ）
- captions ⇄ transcript words の整合（captions 第一級化後、v1.x）
- 無音区間・音量ピークの検出（ffmpeg で決定的に取得可能）

### 実装形

- 小さな CLI（`packages/schemas` 配下または隣接。edit.json + analysis.json を入力に
  PASS/FAIL + 指摘一覧を返す）
- QA ステージスキルとして運用規約化: エージェントは edit.json を書いたら
  **lint → PASS になるまで修正 → その後フレーム視認 → レポート**の順を踏む
- `skills/` に QA スキルは現状存在しない（CLAUDE.md のステージ構想にある QA の初実装となる）

## 2. words への confidence 付与

- analysis.json v0 に**後方互換の任意フィールド**として `words[].confidence` を追加する
  （whisper.cpp の token 確率から復元。version は 0 据え置き）
- 根拠: ASR の誤認識は**タイミング（いつ切るか）にはほぼ効かないが、意味判断
  （言い直し検出・整文・強調選定）には直接効く**。疑うべき箇所を機械的に示せるようにする
- 用途:
  - ビューワーの低信頼度ハイライト（字幕修正 UI の入口。
    notes-2026-07-14 §3 の「タイムスタンプを保ったままテキストだけ直す」と接続）
  - エージェントが整文するとき、どの word を疑って周辺文脈から復元すべきかの材料
- 実装は analyze-footage スキルの改訂のみ（スキーマ変更・ランタイム変更なし）

## 3. 視覚検索（埋め込み）の導入トリガー

- 埋め込み（CLIP 系）による視覚検索は**最適化ではなく機能追加**として捉える:
  キーフレームキャプションに書かれていない視覚的特徴は、キャプションへの grep では
  原理的に引けない
- **導入トリガー**: キーフレームキャプション（`keyframes[].note`）への全文検索の
  取りこぼしが実運用で問題化したとき。それまでは作らない
- 現状はキャプション + grep で足りている前提を維持する

## 4. トランスクリプト編集パネル — 二段構え

notes-2026-07-14 §1 の「transcript と cuts の対応表示 + 編集前/編集後トグル + word 単位の
採否操作」の実装方針。**MVP と本命を分ける**（2026-07-16 オーナー決定）。

### MVP: Monaco デコレーション

- シェルが Theia のため Monaco は同梱済み・追加依存ゼロ
- 守備範囲: word 単位の CSS クラス（カット済み = グレー打ち消し、低 confidence = 下線、
  再生ヘッド追従ハイライト）、クリックでシーク、hover でタイムスタンプ、
  injected text で話者ラベル、view zones で段落間サムネ
- テキスト編集はエディタネイティブ（字幕修正の書き戻しは変更イベントから words へ按分）

### 本命: リッチ専用 UI（Vrew 級）

- Monaco は行ベースレイアウトから逃げられず、範囲ごとのフォントサイズ・カード的な
  リッチ組版・読み取り専用領域のネイティブサポートがない。**Vrew のリッチな編集体験には
  原理的に届かない**ため、専用ウィジェットとして別途作る
- MVP からの移行を安くする条件: **パネルは薄い表示層に徹し、状態は全部
  analysis.json / edit.json 側に置く**（書き戻し規律に乗る）。
  Monaco 版を捨ててもデータ・スキル・lint の資産は全て残る

## 実装順の目安

1. confidence 付与（analyze-footage スキル改訂のみ。最安）
2. edit-lint CLI + QA スキル（エージェント自己検証ループの決定的側を確立）
3. Monaco 版トランスクリプトパネル（M3 インタラクション層の延長、MVP）
4. リッチ専用 UI（本命。3 で運用が回り始めてから要求を固めて着手）
5. 視覚検索（トリガー待ち。着手条件は §3）
